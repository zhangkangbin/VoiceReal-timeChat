# 60 个表情词归一化与手机端匹配方案

版本：1.0.0；日期：2026-10-29。本文记录产品与技术方案，附可读取的词库和映射示例；模型训练和图片制作尚未进行。

实施进度：离线规则匹配与聊天接入现已按本方案的第一阶段实现，详见 [模块使用说明](implementation.md)。以下保留初始规划；语义模型训练、图片和动画属于后续阶段。

## 1. 目标与输入契约

上游大模型已理解用户输入，并返回一个表情词。此模块只把该词转换为当前表情库的资源 ID，不重复分析用户原话。输出只选择一个主表情。

例如：`狂喜 → happy → 开心资源`、`哈哈 → happy`、`心碎 → heartbroken`。不存在“狂喜”资源并不妨碍将它归入开心。

本版定义 60 个通用聊天角色表情标签，涵盖情绪、面部动作、手势和状态。它们不是 60 个天然互斥的心理情绪，而是 60 个可选择的资源。因此需要人工定义相近标签的边界。图片及动画仍待后续制作或绑定。

- 正常输入：一个简短表情词或固定短语，如 `狂喜`、`喜出望外`、`轻轻摇头`。
- 也接受词库中的标准英文 ID，避免已经规范的结果再次经过模型判断。
- 空输入、非字符串、多标签数组属于 `INVALID_INPUT`。明确包含多个表情的输入要求上游选择一个主表情，不随意取第一个。
- 有歧义、语义未知或资源不覆盖时返回 `NO_MATCH`。
- `NO_MATCH` 和 `INVALID_INPUT` 是系统状态，不计入 60 个表情；`neutral / 平静` 是真实表情，不能冒充拒识结果。
- 第一版不从裸 emoji 推断含义，也不扩展到长句、讽刺或多轮上下文分析。

## 2. 推荐架构

```text
上游表情词
    ↓
输入契约检查与保守规范化
    ↓
标准 ID / 标准名称精确匹配
    ↓ 未命中
完整词别名匹配
    ↓ 未命中
歧义词检查
    ↓ 不属于明确歧义词
轻量语义匹配（第二阶段启用）
    ↓
候选分数与分差检查
    ↓
MATCH + 表情 ID / NO_MATCH
    ↓
应用按 ID 查询实际图片或动画资源
```

规范化只处理首尾空白等不改变含义的格式。英文 ID 可统一大小写。不要删掉“不”，不要用子串规则；`不同意` 不能因为包含 `同意` 而匹配点头。多词含义不清时不要通过任意删词来凑标签。

特别兼容规则：整段只有两个或更多“哈”时，如 `哈哈哈哈`，归 `happy`；`哈哈大笑` 不是这个规则的输入，应命中 `laugh` 的完整别名。

标准名称和人工别名命中后立即返回，语义模型无权改写结果。这样 `难过` 不会被相近的 `伤心` 抢走，`狂喜、哈哈` 始终保持映射开心。

语义模型输出的 ID 仍必须存在于当前词库，并且具有可用资源。文件存在性和图片/动画加载失败属于资源层问题，应返回独立错误或不切换，不让分类器猜一张别的图片。

## 3. 词库设计与边界

数据源是 `expressions.v1.json`。每项包含：

| 字段 | 用途 |
|---|---|
| `index` | 人工查看的序号，不作为业务稳定标识 |
| `id` | 稳定资源 ID，例如 `happy`；发布后尽量不改名 |
| `name` | 中文标准名称 |
| `group` | 便于人工管理的分组，不用于硬限制模型候选 |
| `type` | 情绪、面部动作、手势或状态 |
| `description` | 正向含义描述，可用于语义匹配 |
| `aliases` | 已审核、完整输入唯一命中的别名 |
| `boundary` | 产品边界与易混说明，供标注和审阅使用 |

语义原型使用 `name + description` 和精选代表词；不要把含有反例的 `boundary` 直接当作正向同义文本。所有标签使用相同的原型数量与计分策略，避免别名越多越容易抢占结果。

关键边界：

- 开心 / 微笑 / 大笑：开心是通用喜悦；后两者是明确的笑容动作。狂喜、兴奋、哈哈仍归开心。
- 伤心 / 难过 / 哭泣：本版约定为心碎伤痛 / 一般低落 / 明确流泪动作。单词“悲伤”默认归难过。
- 惊讶 / 震惊 / 惊喜：普通意外 / 强烈呆住 / 正向意外。
- 害羞 / 尴尬 / 道歉：羞涩 / 社交窘迫 / 赔不是；“不好意思”单独出现时不强行选择。
- 思考 / 困惑 / 怀疑 / 好奇：主动推敲 / 没理解 / 不相信 / 想了解。
- 感动 / 感谢：被触动的情绪 / 向他人表达谢意。
- 点头 / 摇头 / 拒绝：前两项优先承接明确动作；只说拒绝时选拒绝。
- 鼓励 / 点赞 / 庆祝：支持继续努力 / 认可表现 / 庆贺结果。
- 打招呼 / 告别：单独“挥手”无法判定，返回 `NO_MATCH`。

这些是本项目的标注约定，不是对自然语言的唯一解释；真正资产风格确定后可以调整，但需要同步更新别名、样例和版本。

## 4. 模型与训练路线

### 第一阶段：无模型基线

先启用标准 ID、名称、别名和歧义词规则。本次词库每类有至少 5 个别名，可直接作为实现基线。词库不是训练完成的模型，有限别名也不能保证覆盖所有表达。

第一阶段未命中的词返回 `NO_MATCH`，记录表情词和候选供人工审核即可。输入已经是上游提取出的词，不必为这个模块重复保存原始聊天内容。

若上游支持可靠的结构化输出，可逐步要求它从 60 个 ID 中选择，同时保留匹配模块用于旧版本和异常结果；正确标准 ID 直接通过。

### 第二阶段：预训练中文语义模型

先使用现成中文句向量模型做语义对照，例如 `BAAI/bge-small-zh-v1.5`。它用于验证未见表达能否映射正确，不预先假设它满足最终手机体积预算。标准标签的原型向量提前计算，运行时只计算一个输入词的向量，再比较 60 类原型，无需引入向量数据库。

先使用冻结的预训练模型评测，不必一开始就训练。相似度不是概率，不能因为达到任意固定数值就承诺命中正确。要求最高分超过验证集确定的门槛，并且第一、第二候选有足够分差；歧义词仍由明确规则拒识。

若错误集中在特定近义词或标签边界，再使用本项目词对进行对比微调。训练格式为：

| 表情词 | 正确资源 | 容易混淆的错误资源 |
|---|---|---|
| 狂喜 | 开心 | 大笑、惊喜 |
| 苦笑 | 苦笑 | 微笑、开心 |
| 心碎 | 伤心 | 难过、哭泣 |
| 喜出望外 | 惊喜 | 惊讶、开心 |
| 等烦了 | 不耐烦 | 烦躁、期待 |
| 挥手告别 | 告别 | 打招呼 |

多个资源在自然语言上可能都说得通，只有产品定义明确的样本才能作为困难负例。不要为了凑负例把歧义词硬标成唯一答案。

### 第三阶段：压缩为手机小模型

当语义对照模型效果达标，而手机资源开销不达标时，再压缩：

1. 用已审核的词对和真实未命中词训练；可由较强模型辅助扩充，再人工核对。
2. 比较小型字符 TextCNN / fastText 分类器与小型预训练编码器，使用同一独立测试集。
3. 如需蒸馏，用语义对照模型提供辅助监督，最终标签仍以审核后的标注为准。
4. 固定 60 类的分类器可用作极小体积版本；新增第 61 类通常需重新训练或更新分类头。向量匹配方案新增资源只需增加原型，但仍要重新评测阈值和冲突。
5. 在电脑端训练，在 Android 上推理；比较 FP32/FP16/INT8 版本的效果与资源开销。压缩后的模型必须重新测未知词误触发和相近标签混淆。

不要从零训练一个极小网络就期待它天然理解全部中文同义词。别名表没有的词，必须依靠预训练语义或足够的任务样本来补足。现有模型接口与量化方法须按选定后端验证，不能仅根据“支持 ONNX”推断手机实际可运行。

## 5. 数据准备与评测

本次约 300 个别名是词库种子，不是完整训练集。试验阶段可先为每类收集 10–30 个有区分度的自然表达，但不为满足配额制造牵强同义词；样本不足的类可优先只支持明确名称。

另外收集三组负样本：非表情词（天气、导航）、本版未覆盖状态（头痛）、歧义词（呵呵、不好意思）。这些用于评测和训练拒识，不能强塞进某一表情。

训练、验证、测试按同义表达簇、扩写模板和来源分组划分，而不是随机拆重复变体。同一组“哈哈 / 哈哈哈 / 哈哈哈哈”不得跨集合制造虚高效果。已加入别名表的词只能用于测规则覆盖；评估语义泛化时，必须另外使用未加入别名表且未参与训练的独立词集。

重点记录：

- 标准 ID 和名称的正确率；必须全部精确命中。
- 人工别名覆盖率与歧义词处理正确率。
- 未见表达的 Top-1 命中率与各类召回率，特别查看易混对。
- 自动命中的正确率，以及自动命中覆盖率；提高拒识不能被误报为总体能力变强。
- 无关词、库外词、歧义词被误触发的比例。
- 模型文件大小、tokenizer 大小、总安装增量、峰值内存、冷启动时间、预热后的 P50/P95 延迟。

阈值仅在验证集调优，最终报告使用独立测试集。当前没有真实语料和指定手机，因此不承诺准确率、延迟或 MB 数。

## 6. 接口与现有项目对接建议

建议返回固定结构：

```json
{
  "status": "MATCH",
  "expression_id": "happy",
  "source": "alias",
  "score": null,
  "catalog_version": "1.0.0"
}
```

`source` 可为 `id / name / alias / semantic`。确定性规则不伪造概率，`score` 设为 null；语义分数仅用于调试，注明它不是正确概率。拒识时 `expression_id` 为 null，拒识结果不自动渲染平静表情。

根据项目 README，当前 Android 与服务端通过 WebSocket 交互并已有回合标识。后续接入时可在回合事件中携带表情词，让 Android 本地完成映射；沿用 `turn_id`，避免已取消回合的迟到表情覆盖当前表情。资源表负责 `expression_id → 本地图片或动画`。这是对接建议，本次未核验或改动业务代码。

`NO_MATCH` 时默认不触发新的表情事件。界面是否保持上一状态、多久恢复默认表情，由动画/交互层明确规定，避免拒识结果被误记为平静命中。

## 7. 交付与实施顺序

本次交付：

1. `plan.md`：方案、训练路线、边界和验收方法。
2. `expressions.v1.json`：60 个 ID、名称、定义、别名和匹配约定。
3. `mapping-examples.v1.json`：映射验收示例，不是模型实测成绩。

后续建议顺序：审阅 60 项及其边界 → 绑定真实资源 → 实现规则基线 → 收集真实未命中词 → 评测中文语义对照模型 → 按实际收益决定微调与压缩。不要在词库边界未稳定前投入训练。
